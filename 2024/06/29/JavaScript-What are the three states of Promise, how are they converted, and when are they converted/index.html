What are the three states of Promise, how are they converted, and when are they converted

Foreword

in the process of learning and using promises, understanding its state flow mechanism is a very critical link. Many of The Promise-related bugs are caused by state transitions and timing that are not well understood. This article will analyze the three states of the Promise, the transition logic between the states, and the trigger timing of each state in detail.

The three states of the Promise

A Promise is essentially a state machine with the following three states:

  1. Pending : Initial state, indicating that the task has not been completed
  2. Fulfilled (succeeded) the operation completes successfully and returns the result
  3. Rejected (failed) : The operation failed, and the error reason is returned.

Note: Once the state of the Promise is changed, it is irreversible, that is, the change from pending to fullened or rejected can only occur once.

How is the state transformed?

From Pending → filled

when calling resolve(value) the state changes from pending to fulled and carries the result value value.

From Pending → Rejected

when calling reject(error) the state changes from pending to rejected with error information.

Once the status is determined, it cannot be changed.

timing of State Transitions

the state transition of a Promise does not take effect immediately, asynchronously executed . Even if you immediately call in the constructor. resolve() , the corresponding .then() the callback is also executed in the next event loop.

This is a common pitfall in interviews and reflects the Promise’s microtasking mechanism.

Conditions triggered by then and catch

  • .then(onFulfilled) : Triggers after the Promise is fullfilled
  • .catch(onRejected): Triggered after a Promise is rejected
  • .finally(callback) : whether it is fullfilled or rejected, will trigger

it should be noted that the return value of then and catch is also a new Promise, which can continue to be chained.

State transition rule supplement: errors will also trigger rejected

if an exception is thrown in the executor, it will automatically go to the rejected state.

Interview answer

promises have three states: pending, filled, and rejected. The initial state is pending. After you call resolve, the state becomes fullilled. After you call reject, the state becomes rejected. Once the state changes from pending, it cannot change back, nor can it change from fullfilled to rejected, or vice versa.

The timing of state changes is not synchronized. Even if I call resolve immediately, the callback in the then method will be placed in the micro task queue and executed after the current round of synchronization code is executed. This often causes problems in some combinations of timers and event handlers.

Another detail that is easily overlooked is that the code in the Promise constructor is executed synchronously, but the callbacks in then and catch are asynchronous.

Understanding the flow logic of these three states can help me avoid many pits when dealing with complex asynchronous logic, such as chain calls, error capture, and concurrent processing. At the same time, you can also explain some face questions, such as output order questions, why finally will be executed, etc.

Summary

the state flow rule of the Promise is one of the core of its design. Understanding the definition, conversion method, and execution timing of the pending, filled, and rejected states is a prerequisite for stable and efficient asynchronous programming using promises. Only by mastering these underlying mechanisms can you write robust asynchronous code and answer a variety of Promise questions in an interview with ease.
