What is the request process expressed by the HTTP 304 status code

Foreword

In the HTTP protocol, the 304 status code (Not Modified) is an important part of the caching mechanism. It embodies the negotiation cache process between the client and the server, effectively reduces duplicate data transmission, and improves network performance and user experience. Understanding the request process expressed by the 304 status code will help us gain insight into how browser caching works and how to optimize front-end performance.

This article analyzes the expression of HTTP 304 status codes in the request process in detail, introduces the request and response headers involved, explains the actual request process with examples, and analyzes its advantages and precautions.

The role of HTTP 304 status codes

the main purpose of the 304 status code is to tell the client that the requested resource has not been modified since the last access and that the locally cached data can continue to be used. When the server returns the 304, it does not contain the response body, but only returns the necessary response headers, thus avoiding repeated downloading of complete resources.

Detailed text flow of the 304 request process

  1. Request a resource for the first time
  • the first time the browser requests a resource (such as an image, CSS, JS file), it sends a normal GET request to the server.
  • The server returns the full contents of the resource with cache-related response headers, such Last-Modified (When the resource was last modified) and/or ETag (Resource unique identifier).
  • The browser saves the resource content and this cache information to a local cache.
  1. Subsequent Initiate Conditional Requests

  • when the browser needs to request the same resource next time, it will initiate a conditional request based on the cache information.

  • The browser carries in the request header:

  • If-Modified-Since , the value is returned by the server before Last-Modified time;

  • or If-None-Match , the value is returned by the server before ETag .

  • This means that the browser asks the server to verify that the resource has been modified since it was last acquired.

  1. Server Verify Resource Status

  • after the server receives the conditional request, check the status of the current resource:

  • if resources fromLast-Modified time or corresponding ETag if there has been no change since then, it is judged that the resource has not been modified.

  • If a resource has been modified, it is considered a new resource.

  1. Server returns response

  • when resources are not modified :

  • the server returns the status code 304 Not Modified.

  • The response does not contain resource content and only returns the necessary header information (e. G. Cache-Control , Expires , Last-Modified , ETag etc.).

  • When a resource is modified :

  • the server returns a complete 200 OK response with the latest resource content and the latest cache header.

  1. Browser processing response
  • after receiving the 304 response, the browser determines that the cached resources are still valid, and reads the resources directly from the local cache to complete page rendering without downloading the resources again.
  • After receiving the 200 response, the browser replaces the cache with the new resource content and updates the cache-related header information.
  1. Cache strategy collaboration
  • 304 mechanisms versus strong caching mechanisms (e. G. Cache-Control: max-age ) Work together.
  • The preceding conditional request and 304 response processes are triggered only after the strong cache fails.

Advantages and considerations

advantage

  • reduce duplicate downloads and save bandwidth
  • speed up page loading and improve user experience
  • reduce server load

precautions

  • 304 only the “unmodified” state, the browser still needs a complete request and response process
  • whether the resource hits the cache depends on the exact Last-Modified and ETag generate
  • incorrectly configured cache policies can result in cache invalidation or inconsistent data
  • for dynamic content or frequently changing resources, the cache time should be reasonably controlled to avoid misuse of expired data.

Interview answer

interviewer: What is the request process expressed by the HTTP 304 status code?

Answer:

the HTTP 304 status code indicates that the server notifies the client that the requested resource has not changed since the last access, and the client can continue to use the locally cached version. On the first request, the client normally obtains the resource and cache header (e. G.Last-Modified and ETag ). For subsequent requests, the client carries the conditional request header. If-Modified-Since or If-None-Match to ask the server if the resource is updated. The server determines whether the resource has changed, and if not, returns a 304 response without a response body. After receiving the 304, the client directly uses the cached resources to avoid re-downloading.

This process, called negotiation caching, is an important part of the HTTP caching mechanism, reducing bandwidth usage and improving page loading performance.

Summary

the HTTP 304 status code reflects a cache verification process of conditional requests, which effectively reduces the repeated transmission of network resources through the negotiation Cache mechanism. It relies on the condition header in the request and the cache header in the response to work together to achieve intelligent communication between the client and the server.

Understanding the 304 request process is of great significance for optimizing the performance of Web applications and setting a reasonable cache strategy. In the actual project, should be combined Cache-Control , Expires , ETag and Last-Modified and other cache control headers to create a flexible and efficient cache system.
