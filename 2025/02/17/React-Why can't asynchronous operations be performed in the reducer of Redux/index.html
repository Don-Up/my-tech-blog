Why can’t asynchronous operations be performed in the reducer of Redux

Foreword

Redux is a JavaScript library that focuses on state management. Its core idea is to centrally manage all the state of the application and drive UI updates through predictable data flow. Among the Three Principles of Redux, a very key concept is that the reducer must be pure function .

In actual development, many people will have such questions: why can’t I write asynchronous operations in reducer, such as calling API or using setTimeout? This article will explain why the reducer cannot perform asynchronous operations step by step from the design concept of Redux, the definition of pure functions, the responsibilities of reducer, and the handling of asynchronous side effects.

  • the input is the same, the output must be the same (pure function)
  • should not have side effects (do not rely on or modify external state)

what is a pure function?

Pure Function means under the same input, always get the same output without any side effects . Side effects include, but are not limited to, the following:

  • Asynchronous operations (such as setTimeout, fetch, Promise)
  • modifying a variable or object outside a function
  • access IO (such as DOM, localStorage, file system)
  • log, print, alert

Redux emphasizes that reducers must be pure functions to ensure their predictability, testability, and maintainability.

2. Unable to implement Time Travel (Time Travel debugging)

an important reason why Redux DevTools can implement time travel debugging is that reducers are synchronous and pure: the state at any point in time is determined by action. If the reducer becomes impure, such as relying on asynchronous data, then the same state cannot be reproduced when retracing the historical state.

3. Synchronous data flow design

The design of Redux is based on synchronous, unidirectional data flow. If asynchronous code appears in the reducer, the entire state flow will be interrupted or delayed, which will destroy the stability of the Redux architecture.

The correct way to handle asynchrony: Middleware

Redux provides a middleware mechanism for handling side effects. Through middleware, we can intercept asynchronous logic during action dispatch, and then dispatch a pure action to the reducer after the logic is completed.

redux-thunk

redux-saga

the core role of these middleware is to “pull” asynchronous logic from the reducer, thus maintaining the purity of the reducer.

Interview answer

question: Why can’t asynchronous operations be written in Redux’s reducer?

A: Redux’s reducer is a pure function that must be synchronous and side-effect-free so that Redux can guarantee the predictability of state updates. Asynchronous operations, such as fetch and setTimeout, break the pure function feature of the reducer, causing the reducer to fail to return the new state immediately, and also affecting the time travel debugging function of Redux DevTools. Therefore, Redux requires that asynchronous logic be moved into the middleware for processing, such as redux-thunk or redux-saga, while reducer only handles the final synchronous action.

Summary

the design principle of Redux requires that the reducer must be a pure function, and it should not contain any asynchronous or side-effect operations. The benefits of this are:

  • predictable status updates
  • easy to debug and test
  • support time travel debugging
  • simplify data flow structure

asynchronous operations should be handled in the Redux middleware, which is an important manifestation of the separation of functional responsibilities in the Redux architecture. Only by strictly following these design principles can Redux’s advantages and maintainability in large-scale applications be brought into play.
