How does react handle component updates and rendering

Foreword

in modern front-end development, React is popular for its declarative, componentized programming model. However, to truly understand the performance optimization mechanism and Operation Principle of React, one of the core issues that cannot be avoided is: when the state or props of the component changes, how does React update and re-render the component?

This problem not only affects the basic operation mechanism of React, but also affects how we write more efficient and maintainable code. This article will focus on the whole process of component update, from the trigger of data changes, the scheduling of the Fiber architecture, and the final change of DOM, to comprehensively analyze the update and rendering process of React.

First, the update trigger: the state or attribute changes.

React updates are usually triggered by the following conditions:

  • this.setState() call (Class Component)
  • useState() the setter is called (function component)
  • changes to the props passed in by the parent component
  • change in context value
  • force Update ( forceUpdate() )

no matter which entry it is, it essentially notifies React that “the current component needs to be updated”.

Take the function component as an example:

when the button is clicked, setCountTriggered, React starts scheduling the component update process.

Second, the scheduling phase: build a new Fiber tree.

React 16 introduces the Fiber architecture, which transforms the original synchronous recursive update process into an interruptible and recoverable linked list update architecture. This phase is called render phase , is “virtual” and will not directly operate DOM.

The whole process is as follows:

  1. mark the Fiber node to be updated (such as the current component)
  2. recursively traverse and build a new Fiber tree (beginWork stage)
  3. compare the difference between the old and new Fiber trees (diff algorithm)
  4. record the actions that need to be changed (called the effect list)

this phase supports priority scheduling and task sharding , can be interrupted (such as responding to user interaction) to avoid page stuck.

third, the submission phase: DOM update

when the render phase is complete, React enters the commit phase, which is an uninterruptible phase that performs the following operations:

  1. perform DOM update (insert, delete, modify, etc.)
  2. call life cycle or side effects (such useEffect ,componentDidUpdate )
  3. update pointer and state in Fiber linked list

the entire process is executed synchronously, ensuring atomicity and consistency of updates.

This means that in the same event loop, the update of a component contains:

  • build and compare new virtual structures
  • application update to real DOM
  • calling side-effect Hook and Lifecycle methods

four, React how to optimize the update process

React improves update efficiency through the following mechanisms:

1. Virtual DOM + Diff algorithm

React does not directly modify the real DOM, but first compares the changed area by building a virtual DOM, and then minimize DOM operations .

React’s diff algorithm has the following assumptions to improve efficiency:

  • only nodes of the same level are compared.
  • Only nodes of the same type compare attributes
  • by key to optimize node reuse and rearrangement

2. Fiber architecture supports Task interruption and priority

React can assign different priorities according to the urgency of the task, and realize the rendering scheduling mechanism of response priority.

For example:

  • user input → high priority → Fast Response
  • background data load → low priority → idle processing

this keeps the page from blocking user interaction with a large number of low-priority tasks.

3. Batch Update

React automatically merges multiple setstates to reduce the performance overhead caused by multiple renders.

The above two updates will be processed together in one scheduling cycle instead of triggering two re-rendering.

Fifth, the update difference between class components and function components.

Both essentially follow the same Fiber update mechanism, but there are differences in triggering updates and side-effect calls:

interview answer: How does React handle component updates and rendering?

Answer:

React is used. Data-driven + Fiber architecture the update mechanism. When the state or props of a component changes, the update process is triggered:

  1. React marks the current component as “dirty” and begins the render phase
  2. the render phase builds a new Fiber tree, performs diff comparisons, generates an effect list, and records all required change operations.
  3. Enter the commit phase, apply the change to the real DOM, and execute the side effect function

the entire process is divided into an interruptible render phase and an uninterruptible commit phase to ensure fluency and consistency.

React also improves performance and reduces unnecessary rendering operations through Virtual DOM, key matching, priority scheduling, batch update, and other means.

Summary

The process of React handling component updates and rendering is essentially:

  • data update triggers re-rendering
  • the render phase builds a new virtual structure (Fiber tree)
  • diff compares the old and new trees and records the parts that need to be updated
  • the commit phase performs DOM updates synchronously with side effects.

Understanding this mechanism not only helps you write more efficient components, but also provides a deeper understanding of important practices such as Hook execution timing, performance optimization strategies, and component packaging methods. React’s high performance and flexibility are due to its fine update scheduling and rendering control capabilities.
